# SkipAd 设计文档

> 本文档是整个项目的演化蓝图。每个里程碑开工前先在这里补细节，避免边写边漂。
> 对应用户三大关切：① 更大程度的广告跳过能力；② 截屏/录屏辅助生成跳过脚本；③ 跳过按钮位置变化的应对。

## 1. 总体架构

```
┌─────────────────────────────────────────────────────┐
│  UI 层（MainActivity / 快照查看器 / 规则编辑器）      │
├─────────────────────────────────────────────────────┤
│  引擎层                                              │
│   SkipAccessibilityService                           │
│   ├─ 事件节流器（150ms 时间窗 + 包名黑名单粗筛）      │
│   ├─ NodeScanner（五层匹配，见 §2）                  │
│   ├─ ClickPerformer（ACTION_CLICK → 祖先 → 手势）    │
│   └─ 快照/截屏采集器（M3，takeScreenshot + dump）     │
├─────────────────────────────────────────────────────┤
│  数据层                                              │
│   SkipRule（规则模型）  StatsStore（统计/日志）       │
│   RuleStore（M2：JSON 规则导入导出/订阅）             │
└─────────────────────────────────────────────────────┘
```

## 2. 五层匹配策略（回应"更大程度实现广告跳过"）

按命中率与安全度排序，逐层降级：

| 层 | 手段 | 覆盖场景 | 状态 |
|---|---|---|---|
| L1 | 多语言关键字包含匹配（跳过/跳過/スキップ/건너뛰기/skip + contentDescription） | 80% 常规开屏；**位置怎么变都能找到**（按特征找节点，坐标跟随节点） | ✅ |
| L2 | 倒计时正则（"3s 跳过""5 秒后跳过""Skip 5s"） | L1 覆盖不到的倒排文案 | ✅ |
| L3 | per-App viewId 规则（`com.xxx:id/skip_btn`） | 图片型/无文本按钮 | ✅ |
| L4 | per-App 相对坐标（**角落锚定 + 屏幕比例**，非绝对像素） | WebView 渲染的开屏（节点树里只有 WebView 壳） | ✅ |
| L5 | 端侧 OCR（ML Kit / Paddle），对 L4 场景截图识别"跳过"字样后按识别框点击 | WebView 内动态广告位 | 未做 |

> **现状（0.17.x，与本表的关系）**：L1/L2 已收进「开屏窗口」硬边界 ——
> 只有 App 真的切到前台的头 4 秒内，内置词表才参与匹配；窗口之外一条都不用，
> 只认用户从快照点选生成的规则。这是 0.17.0 撤掉全局词表扫描的原因：
> 它在聊天页、信息流里也会命中短文本。L3/L4 只在用户为该 App 建了规则时存在。
>
> 位置证据（0.17.24）：文字规则记录用户点选时按钮的四边占屏比例（`zone*`），
> 命中节点必须落在这块区域附近才动手，取代了此前「屏幕正中一律算正文」的几何粗闸。
> 0.17.25 起同时记录记录时的屏幕方向（`zoneLand`），方向不一致时这一层约束不参与，
> 避免横竖屏互转后整条规则静默失配。

> **开屏窗口与续窗（0.17.53–0.17.56）**：窗口默认只从「真的切到这个 App」起算 4 秒。
> 但有些 App 把开屏拆成两段、且都在自己包里（360 清理大师：`SplashActivity` →
> `SplashRecommendActivity`）。第一段点掉后窗口立即关闭，第二段是同包换页，
> `freshSwitch` 要求「上一屏不是自己」，拿不到新窗口，整段不在射程内。
>
> 0.17.53 起加**续窗**：点击成功时记下时刻与当时的 Activity，若 6 秒内**同包**、
> **Activity 变了**，则清掉关窗标记、重置计时、再开一次窗口——**一轮只允许续一次**
> （`retriedAfterHit` 标记，真切换到这个 App 时清掉）。没有选择延长 `SPLASH_WINDOW_MS`：
> 那会让所有 App 的主界面都多扫两秒，而真正需要续扫的只有「刚点完又同包换页」这一种形态。
>
> 续窗必须同时清掉三层闸门，少一层就是空转（这层教训花了四个版本）：
> `ruleState` 里的规则冷却、`lastSkipPkg` 的同 App 冷却（`COOLDOWN_MS=4000`，
> **完全不经过 `ruleState`**）、以及 `clickedRects`（由 `onPageChanged` 清）。
> `lastSkipAt` 不能清 0——它还被 `landedOnAdPage` 用来判断「点击后 3 秒内有没有下载类 CTA」。

防误触三保险（所有层共用，硬约束）：
1. 文本长度上限（24 字）：广告正文里提"跳过"的不是按钮；
2. 可点击祖先面积占屏上限（12%）：广告大图上印的假"跳过"直接排除；
3. 会话冷却（同窗口 4s）：跳过成功后不再动作，防误点二级页。

## 3. 稳定性设计

- 事件风暴：`TYPE_WINDOW_CONTENT_CHANGED` 一次开屏可触发上百个 → 全局 150ms 节流 + 包名黑名单（systemui/launcher 先排除）+ 遍历双上限（800 节点 / 400ms）。
- **桌面动态拉黑**（0.3.0）：静态包名黑名单会漏厂商桌面（荣耀桌面漏了 → 主屏「SkipAd」图标文字含 skip 被连点 6 次），改为 `CATEGORY_HOME` 动态解析全部桌面应用拉黑，桌面无开屏广告还可省遍历开销。
- `rootInActiveWindow` 优先于 `event.source`（后者在 CONTENT_CHANGED 中可能是局部节点）。
- 不调用 `AccessibilityNodeInfo.recycle()`：API 33+ 已废弃，低版本不回收仅轻微内存压力，规避 recycle 误用崩溃。
- 服务被杀：分级保活（§3.1）。未授权时 UI 检测"服务未连接"→ 引导跳设置页；授权静默后自动复活。
- **状态机与时间窗的改动，必须用受控 App 串起来跑一遍再发版**（0.17.53–0.17.56 教训）：
  同一个「续窗」机制被三层障碍卡住，每层单独看都像唯一障碍——换页判据用了被 `isSystemUiClass`
  过滤后的类名、防重入因为没有独立标记而失效（每次点击都会重写凭据）、两层冷却未清。
  四个版本依次修完，而**编译、单测、CI 自始至终全绿**，没有一个错能在静态检查里暴露。
  受控工程在 `H:\skiptest`，含 `TwoStageSplashActivity` → `SecondAdActivity` → `ThirdAdActivity`
  三连跳变体（第三段用来验证「只续一次」）。改这块逻辑先去那里复跑，不要等广告位。

### 3.1 无障碍保活（✅ 0.2.0 实装，提前自 M3/M4）

无障碍服务被 ROM 杀 / 开机拦绑定 / 升级被强制关闭，是这类 App 的头号痛点。分级方案：

| 模式 | 前提 | 行为 |
|---|---|---|
| 静默复活 | adb 授 WRITE_SECURE_SETTINGS（signature 级，正常安装拿不到） | 掉线时把服务写回 enabled_accessibility_services + accessibility_enabled=1，系统自动重绑 |
| 提醒模式 | 零授权（默认） | 掉线发本地通知，点按跳系统无障碍设置 |

- 触发源收敛到 `KeepAlive.checkAndRecover`：**服务 `onUnbind`（黄金几秒，延迟 1.5s 自检）**、BOOT_COMPLETED / MY_PACKAGE_REPLACED 广播、15 分钟周期 Job（JobScheduler persisted，跨重启）、UI「立即自检」；
- **三重防震荡**（真机实测教训）：复活冷却 30s（系统重绑过渡期 `isRunningNow` 滞后 false，否则震荡成活循环）、`scheduleJob` 幂等（重排周期 Job 会触发立即首跑，与重绑滞后叠加成反馈回路）、两段式写入仅在"配置在但没绑定"场景启用；
- **两段式写入**是关键细节：开机被 ROM 拦绑定时配置里服务还在，值不变系统不重新解析——先写"去掉自己"再写"加回自己"制造一次变更，系统才会重新绑定；
- 边界：用户主动关闭在静默模式下也会被拉起（授权即视为接受）；强停后 App 进 stopped 态、一切调度失效，打开一次 App 恢复；
- 零依赖：用原生 JobScheduler 不引 WorkManager；不需要前台服务（服务绑定期间进程本身受系统保护）。



目标：把"写一条 per-App 规则"的成本从"会无障碍开发"降到"点两下屏幕"。

### 4.1 节点快照 + 截屏（M3 核心，走无障碍自带能力，零新权限）

- `AccessibilityService.takeScreenshot()`（**API 30+**，无障碍服务原生 API，**不需要 MediaProjection、不需要存储权限**，回调给 Bitmap）；
- 同时 dump 当前窗口节点树（text / contentDescription / viewIdResourceName / className / bounds / clickable）成 JSON；
- 两者时间对齐打包成一份"快照"（GKD 同款思路），存 App 私有目录；
- **快照查看器**：App 内页展示截图，节点 bounds 画半透明框叠加，点选任一节点即生成对应规则（viewId 优先、文本兜底、desc 兜底），一键保存并立即生效；
- 触发方式：通知栏常驻"抓取快照"动作 / 无障碍快捷方式（AccessibilityShortcut，长按音量键）。

### 4.2 录屏时序分析（M3.5，降级实现）

- 原始方案：MediaProjection 录制整个开屏过程 → 逐帧回放定位"跳过按钮首次出现的时刻"→ 自动给规则加 `actionDelay`；
- 降级方案（零权限优先）：**高频快照序列**——在检测到目标 App 开屏 Activity 时自动连续抓 N 张截图（如 500ms × 10 张），回放时人工/半自动选帧，效果等价且不引 MediaProjection；
- 录屏方案保留为可选高级功能（用户显式授权时才启用）。

### 4.3 快照分享

导出快照（截图+JSON 打包）为单文件，便于换机调试与社区互助定位问题节点。

## 5. 规则格式（M2 冻结）

```json5
{
  "version": 1,
  "rules": [
    {
      "id": "com.xxx.splash",
      "app": "com.xxx",                 // 缺省 = 全局规则
      "activityPrefix": "Ad",           // 可选：限定 Activity（粗筛提性能）
      "match": {
        "textContains": ["跳过"],
        "viewId": "com.xxx:id/skip",
        "regex": ["(?i)skip\\s*\\d"]
      },
      "anchor": { "corner": "topRight", "xRatio": 0.92, "yRatio": 0.08 },  // L4 坐标：四角锚定+比例，换分辨率不失效
      "maxAreaRatio": 0.12,
      "actionDelay": 0,
      "enabled": true
    }
  ]
}
```

- 位置变化的应对总结：**L1/L2/L3 按特征找节点，天然跟随位置**；只有 L4 用坐标，而 L4 用"四角锚定 + 比例"，同一广告 SDK 四角随机也只需把 corner 写成候选数组；
- 社区兼容评估：GKD 订阅是类 CSS 选择器体系（GPL 项目，只借鉴思路不搬代码），LiTiaotiao 社区规则是文本 DSL——M2 先定自家 JSON，M4 评估写转换器白嫖社区规则。

## 6. 已知红线与不做清单

- 不申请 INTERNET / 存储 / 位置权限，永远；保活相关的 RECEIVE_BOOT_COMPLETED / POST_NOTIFICATIONS / WRITE_SECURE_SETTINGS 属运营性权限（不碰用户数据，后者还必须 adb 手动授予才生效），不在红线内；
- 不做"自动抢红包/砍价/拉活"等灰产自动化，专注跳广告与关弹窗；
- 不上架国内应用商店（李跳跳 2023 年前车之鉴），发布渠道 = GitHub Release + APK；
- GPL 项目的代码不抄（GKD），MIT 项目（Android-Touch-Helper）可借鉴，借鉴处在 CHANGELOG 致谢。

## 8. 当前已知缺口（截至 0.17.56）

按「会不会真的咬人」排序，不是待办清单：

1. **右上角启发式是几何猜测，不可能零风险**：它在开屏窗口内、切前台 2.5 秒内，按「右上角、小、可点击」找按钮。已有五道约束（黑名单 / 预热 20s / 2.5s 时间闸 / 任意可滚动整页放弃 / 用户开关），但没有文本和 id 证据。0.17.33 起它不再补刀（`maxRetry=0`），判错一次最多点一下。用户关掉「内置词表」开关即彻底停用。
2. **viewId 通道依赖广告 SDK 的命名**：0.17.33 起要求「SDK 前缀 + 关闭语义」双命中，`gdt_btn_download` 这类广告 CTA 不再命中；代价是 SDK 若把关闭钮命名成 `gdt_btn_x` 这种无语义名字就会漏。漏跳可接受，误点不可。
3. **测试只覆盖纯逻辑**：0.17.46 起 `src/test` 有 15 个用例（viewId 判定、文本长度闸、内置规则 id 契约，以及 `tt_` 业务关闭钮必须拒绝、`bsyad_`/`mimo_` 关闭钮命中两组），跑在 CI 的 `testDebugUnitTest`。`NodeScanner` 的面积/位置判定、`CornerSkipFinder` 的几何闸、核验的包名判定仍无测试——它们要么依赖 `AccessibilityNodeInfo`，要么依赖真实跳转时序，得先抽函数或上设备测试才能覆盖。
4. **zone 对显示大小的适应性**：只处理了方向，没处理「用户改了显示大小或分辨率」导致的纵向比例偏移，靠 8%/12% 容差硬吃。0.17.33 已把扫描基准统一到 `realScreenPx()`（与记录口径一致），但显示大小变化仍未覆盖。
5. **`SkipAccessibilityService` 约 2400 行**，同时承担跳过引擎、快照抓取（约 300 行）、悬浮钮回调、保活通知、节点路径查找、坐标规则。改动风险集中在这一个文件；拆分会牵动服务生命周期，暂不做。
6. **构造场景为主**：真实开屏广告的验证样本有限，主要靠快照回放与人工构造。0.17.30–0.17.32 的两次误点都是真机跑出来的——构造场景测得出「能不能跳」，测不出「会不会点错」。
7. **诊断落盘有写放大**：`EngineTrace` 每条都 flush，开屏窗口内每秒十几条。文件数与行数有限（3 份 × 300 行），但不是零成本。
8. **核验只在能复现的前提下成立**：0.17.38 起内置规则命中也会复核（同扫描器、同规则 id、同页面），但它只回答「同一个词还在不在」。如果广告本身把「跳过」画在图片里、或点击区域不是文字所在的节点，复核会一直判「还在」然后 giveup——不再虚报成功，但也帮不上把它点掉。
9. **多窗口扫描的边界**：0.17.37 起主窗口没命中时会再看最多 2 个同包窗口，但只限开屏窗口内。
10. **WebView 不是盲区（0.17.44 实测结论，推翻此前的判断）**：受控 App 里放一个 `loadDataWithBaseURL` 的 WebView，HTML 里画一个「跳过」。第一次扫描（44ms）`nodes=2 texts=[]`——DOM 还没挂到无障碍树上；174ms 后热窗口的下一次主动扫描就命中了，用的是纯文本规则（`规则=splash-common-text`），与元素的 id 无关。也就是说标准 WebView 的 DOM 是暴露的，只存在「晚到一百多毫秒」的时序问题，而 120ms 的主动扫描节拍本来就盖得住。**因此 L5 OCR 对这类 H5 开屏不必要**。仍然扫不到的只剩真正没有 DOM 的形态：视频开屏用 SurfaceView/TextureView 渲染、或 SDK 主动把 WebView 标成 `importantForAccessibility=no`。
11. **同包落地页只按 CTA 文案判**：0.17.40 起「点击后换页 + 新页面出现下载/安装 CTA」判为疑似点进广告。它是启发式：落地页上没有那几种说法（比如只放一张图和品牌名）就判不出来，会当成真跳过；反过来，如果某个 App 的确会在跳过后落到带「立即下载」的自家页面，就会少记一次。两边的代价都是统计口径，不是点击行为。
12. **「冷启动」必须确认进程真的死了（0.17.45 排查教训）**：曾一度判定微博「对第三方无障碍零事件」，理由是冷启动后引擎日志 0 行、滑动也没有。**这个结论是错的**。按「先 `am force-stop`、确认 `pidof` 为空、再从 `.SplashActivity` 启动」重测，事件正常到达：`wsc ... prev=com.miui.home fresh=true cls=com.sina.weibo.SplashActivity` → `hot-open`。之前的 0 行是因为 App 只是从后台被唤回，没有产生新的窗口状态事件。
    真正要注意的是另一件事：`freshSwitch` 要求 `prev != 当前包`。如果杀进程后桌面切换事件没被观察到，`prev` 仍是同一个包，开屏窗口不会打开——表现同样是「不跳」。用桌面或另一个 App 过一手再启动即可；日常从桌面点图标本来就是这个顺序。
13. **viewId 特征库的证据有天花板（0.17.46 复核结论）**：ARSC id 全表能回答「这个 id 名在包里存在」，回答不了「它被哪个布局用、是不是开屏那个按钮」。49 个样本里 `tt_` 覆盖 31 个包，但含 close 的 24 个 id 中只有 4 个属于真穿山甲，其余是淘宝 3D 试穿、支付弹窗取消这类业务控件——纯静态数据只能靠命名语义猜，所以 `tt_` 已移除。判断任何前缀该不该加，先问它在 `skip` 规则之外还剩什么增量。
14. **部分样本的布局 XML 根本不在 APK 里**：淘宝 1468 个 layout 资源、京东 200 个，在 zip 里找不到对应文件（重动态化，开屏走 Weex/WebView/纯图片）。这类 App 靠 viewId 静态提取天然无效，只能靠文本规则与坐标兜底。另外 49 个 APK 里 7 个资源严重残缺（京东仅 774 个 id、快手极速版 763、WPS lite 823、护眼仪 0），占 14%——基于这些包得出的「有/没有某 SDK」结论不可信。
15. **开屏可能不在目标 App 自己的包名里（小米）**：HyperOS 会把开屏交给 `com.miui.systemAdSolution` 渲染。它不是「没有广告」，是广告换了宿主，而引擎原来只认「有启动图标或桌面」的包，它两样都不满足，于是 WSC 分支整段被跳过，最后静默 return。0.17.48 用 `SYSTEM_AD_GATEWAYS` 豁免，实测能跳过（倒计时「跳过 | 3」时点击，0.4 秒回主界面）。**但只收有实机节点证据的包名**：华为、OPPO、vivo、荣耀都有各自的开屏容器，本机拿不到那些设备的节点树，凭包名猜着加等于把未验证的名字当证据。
16. **排查「某 App 完全不跳」先看 logcat 缓冲区（0.17.48 教训）**：测京东时连续三次「引擎零日志」，一度怀疑 Android 11 包可见性让 `getLaunchIntentForPackage` 返回 null。实际是 logcat 环形缓冲区被京东冷启动的 36 万字符日志冲掉了，SkipAd 的 VERBOSE 日志全被挤出去。`adb shell logcat -G 16M` 后同一操作立刻正常。同理，0.17.51 之前 `scanAndAct` 有两处静默 return（拿不到 root、热窗口内无规则），一点痕迹都不留，现在都记 `reject=no-root` / `reject=no-rule-in-hot`，且只在 `isHot` 为真时记，避免刷屏。
17. **日志的数值精度会主动误导人（0.17.52 教训）**：面积日志原本是 `(area / screenArea * 100).toInt()`，整数截断让**所有小于 1% 的节点都显示成「面积0%」**。1220×2712 的屏上 1% 是三万三千平方像素，0.99% 也有 180×180——一个完全正常的按钮，在日志里和 1 平方像素的碎屑长得一模一样。0.17.51 排查时据此判成「极小节点被误点」，差点去收紧面积闸，读了代码才发现只是打印精度。现在改打像素尺寸（`126x64`）。判断逻辑没动：`area in 1f..screenArea * maxAreaRatio` 的下限确实是 1 平方像素、很松，但收紧需要真实误点的尺寸证据，不能凭「一行可疑日志」就改。
18. **启动页自带的「跳过」会被计数（0.17.52 观察，样本 1 次）**：清理大师冷启动时，引擎在 `SplashAdActivity` 出现前 86ms 点了它启动页上的「跳过」（`126x64`，`规则=splash-common-text`），核验通过并记了一次 `verified`。点的是 App 自己的启动页跳转按钮，不是广告，点下去也符合用户预期，所以不算危险；但统计里会计成一次「跳过广告」。现在只有一次样本，不凭一次就加规则——要剪清「启动页跳过」与「开屏广告跳过」得先看到更多形态。
19. **开屏可能是多段、且都在同一个包里（0.17.53–0.17.56 实测）**：360 清理大师是 `SplashActivity`（2–3.2s）→ `SplashRecommendActivity`（4.5–6.3s）→ `MainActivity`。第一段点掉时窗口关闭，第二段同包换页 `freshSwitch=false` 拿不到新窗口；时间上第二段出现时 4 秒窗口只剩 65ms。续窗一次可解决，但有两个残留风险：① 点击后主界面若恰好换了 Activity，也会触发这一次续窗，代价是多扫四秒（只有当主界面上确实有「跳过」两字才会点下去）；② 6 秒有效期是拿 360 的 493ms 定的经验值，真实 App 若第二段延迟超过 6 秒仍会漏。
20. **续窗只在受控 App 上验证过，真实 360 仍未验证（截至 0.17.56）**：受控环境里三段之间只隔 490ms，且页面没有网络、没有 SDK 初始化；真实 360 第二段前的 `nodes=1` 持续了 1.8 秒，而受控 App 只有 80ms。节点树建得慢时，550ms 的第二段可能扫不到任何东西。要等广告位恢复后冷启动，看日志里第二段有没有 `HIT`。
